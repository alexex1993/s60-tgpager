# Telegram-пейджер из Nokia N70: Symbian C++, два TCP-соединения и Python-прокси

У Nokia N70 всё ещё есть экран, клавиатура и возможность установить нативное приложение. Для коротких сообщений этого достаточно. Проблемы начинаются, когда на другом конце соединения оказывается современный сервис с HTTPS, JSON и постоянно меняющимся API.

TgPager связывает эти два мира: на телефоне работает небольшое приложение для Symbian, на сервере — Python-прокси, а собеседник пишет обычному Telegram-боту. Сообщение появляется на Nokia; ответ можно набрать с её клавиатуры. Получается двусторонний пейджер.

Код проекта написал LLM-агент. В этой статье разберём его устройство и инженерные трудности: старый SDK, асинхронную модель Symbian, кириллицу в ресурсах, передачу строк поверх TCP и баг, из-за которого сообщения существовали в памяти, но выглядели пустыми на экране.

Разбор опирается на исходники, инструкции сборки и историю Git. Там, где сохранилось исправление, можно показать конкретные изменения. Там, где есть только ограничение среды или особенность реализации, не будем придумывать хронологию отладки и число неудачных попыток.

## Что умеет пейджер

Сценарий использования выглядит так:

1. Собеседник отправляет текст Telegram-боту.
2. Сервер забирает сообщение и передаёт его приложению на Nokia.
3. Телефон добавляет текст в историю с префиксом `Бот:` и показывает всплывающее уведомление.
4. В меню «Написать» можно набрать ответ. В Telegram он придёт от бота.

На телефоне есть настройки адреса сервера, порта и кода доступа, подключение и отключение, очистка истории. После запуска приложение подключается автоматически, если адрес уже сохранён. При обнаруженном обрыве приёмного соединения предусмотрено переподключение.

Обмен идёт через один бот и общий серверный буфер. Входящие тексты ограничены 400 символами по умолчанию; редактор исходящих сообщений — 200 единицами UTF-16. Фотографии, голосовые сообщения, файлы и редактирование сообщений в этот сценарий не входят.

Пользовательский Telegram-аккаунт на телефоне не авторизуется. На сервере используется Bot API, поэтому приложение показывает только сообщения, поступающие этому боту. Диалоги основного аккаунта оно не загружает.

## Главная граница архитектуры: современный API остаётся на сервере

Проект состоит из двух частей:

- `TgPager/` — нативное C++-приложение для S60 2nd Edition Feature Pack 3, Symbian 8.1a.
- `server/tg_proxy.py` — TCP-прокси на Python 3, использующий только стандартную библиотеку. Целевая серверная среда — Debian 13.

Общая схема:

```text
┌──────────────────────────────┐
│ Nokia N70                    │
│                              │
│ Avkon UI                     │
│   ↕                          │
│ CTgEngine                    │
│   ├─ CTgPollConn ────────────┼── TCP: AUTH, POLL ────┐
│   └─ CTgSendConn ────────────┼── TCP: AUTH, SEND ────┤
└──────────────────────────────┘                       │
                                                      ↕
                                      ┌──────────────────────────┐
                                      │ Python-прокси            │
                                      │                          │
                                      │ TCP-обработчики          │
                                      │ общая очередь сообщений  │
                                      │ фоновый getUpdates       │
                                      └────────────┬─────────────┘
                                                   ↕ HTTPS / JSON
                                      ┌──────────────────────────┐
                                      │ Telegram Bot API         │
                                      │ getUpdates / sendMessage │
                                      └────────────┬─────────────┘
                                                   ↕
                                      Чат собеседника с ботом
```

Телефон знает адрес собственного сервера и несколько текстовых команд. Токен бота, JSON и обращения к Telegram остаются в прокси.

Публичный Telegram Bot API требует HTTPS. В этой реализации клиент на N70 использует обычный TCP и не решает задачу совместимости старого TLS-стека с современным сервисом. Эту обязанность выполняет серверная `urllib.request`. Требование HTTPS описано в [документации Bot API](https://core.telegram.org/bots/api#making-requests).

Фразу «телефон не умеет TLS», встречающуюся в описании проекта, полезно понимать именно в этом контексте: в TgPager современное HTTPS-соединение вынесено с телефона. Из кода проекта нельзя сделать вывод об отсутствии любых SSL/TLS-возможностей у всей платформы Symbian.

Такое разделение оставляет клиент компактным. Он занимается вводом, отображением, кодировкой и состоянием двух соединений. Если Telegram поменяет параметры метода отправки, менять нужно будет прежде всего серверную часть.

У решения есть цена: участок Nokia → прокси передаёт и сообщения, и код доступа открытым текстом. `AUTH` проверяет знание общего секрета, но не шифрует транспорт. Это существенная граница применения пейджера: такая схема не обеспечивает конфиденциальность переписки на всём пути.

## Почему у телефона два TCP-соединения

Пейджер должен ждать входящие сообщения и одновременно позволять отправить ответ. В TgPager эти задачи разделены между двумя соединениями.

**Приёмное соединение живёт долго.** После авторизации телефон отправляет `POLL`. Сервер отвечает сразу, если в очереди есть сообщения, либо ждёт их до 50 секунд. Завершив ответ, сервер присылает `END`. Телефон сразу отправляет следующий `POLL` по тому же сокету.

**Соединение отправки создаётся для отдельного сообщения.** Телефон подключается, проходит `AUTH`, передаёт `SEND`, получает результат и закрывает сокет.

TCP позволяет обмениваться данными в обе стороны и на одном соединении. Но для этого протокола один канал потребовал бы дополнительного решения: как обрабатывать `SEND`, пока серверный обработчик ждёт результат `POLL`, и как сопоставлять перемешанные ответы с запросами. Два сокета позволяют оставить последовательную логику на каждом из них.

Приёмный канал занят ожиданием. Отправляющий выполняет короткую отдельную операцию. На телефоне им соответствуют два active object, а на сервере — два клиентских потока.

Оба соединения инициирует Nokia. Сервер отвечает по уже открытому каналу; входящее подключение к телефону ему не требуется. Это подходит для мобильного доступа, при котором телефон не имеет доступного извне адреса.

## Протокол: три команды и явный конец ответа

Между телефоном и прокси нет HTTP. Используются строки UTF-8, каждая заканчивается байтом LF, то есть `0x0A`.

| Команда | Назначение | Ответ |
| --- | --- | --- |
| `AUTH <код>` | Первая команда в каждом соединении | `OK` или `ERR auth` |
| `SEND <текст>` | Отправить текст в Telegram | `OK`, `ERR nochat` или `ERR telegram` |
| `POLL` | Получить накопившиеся тексты или дождаться новых | Ноль или больше строк `MSG <текст>`, затем `END` |

Если `REQUIRE_CODE` на сервере пуст, авторизация всё равно выполняется. Клиент отправляет `AUTH ` с пустым кодом, и сервер отвечает `OK`.

Сессия отправки выглядит так. Стрелки здесь обозначают направление обмена и в протокол не входят:

```text
N70 → прокси: AUTH example-code
прокси → N70: OK
N70 → прокси: SEND Привет с Nokia!
прокси → N70: OK
```

`OK` после `SEND` означает успешный вызов Telegram `sendMessage` со стороны прокси. Это не подтверждение прочтения собеседником.

Приём:

```text
N70 → прокси: AUTH example-code
прокси → N70: OK
N70 → прокси: POLL
прокси → N70: MSG Ты на связи?
прокси → N70: MSG Проверка пейджера
прокси → N70: END
N70 → прокси: POLL
...ожидание следующего сообщения...
```

После пустого ожидания сервер отправляет только `END`. Соединение остаётся открытым.

### Зачем экранировать текст

Перевод строки завершает команду. Если передать его внутри сообщения как есть, одна полезная нагрузка превратится в несколько строк протокола. Поэтому действуют два правила:

| Исходный символ | Представление в полезной нагрузке |
| --- | --- |
| Обратный слеш `\` | `\\` |
| Перевод строки | Два символа `\n` |

Например, сообщение из двух строк:

```text
Первая строка
Путь: C:\temp
```

передаётся одной строкой:

```text
MSG Первая строка\nПуть: C:\\temp
```

Сам терминатор после этой строки остаётся настоящим LF.

В Python порядок замен задан явно:

```python
def escape_text(text: str) -> str:
    return text.replace("\\", "\\\\").replace("\n", "\\n")
```

Сначала экранируется обратный слеш, затем перевод строки. Обратное преобразование реализовано последовательным разбором символов, чтобы различать настоящий перевод строки и буквальный текст `\n`.

При показе на Nokia декодер заменяет экранированный перевод строки пробелом. Многострочный текст передаётся через протокол, но в истории телефона превращается в один текстовый поток с переносами по ширине списка.

### TCP не сохраняет границы строк

Даже у такого маленького протокола есть важная транспортная сложность. Один вызов чтения может вернуть половину команды, несколько команд сразу или фрагмент многобайтового символа UTF-8.

Клиентская `CTgConn::Feed()` сначала накапливает байты в `iLine8`. Только после LF готовая строка попадает в обработчик. Серверная `recv_line()` делает то же самое через `bytearray`, сохраняя остаток для следующего чтения.

Так кириллический символ, разрезанный между двумя чтениями сокета, не приходится декодировать по частям. Сначала собирается строка байтов, затем обрабатывается UTF-8.

У клиентской строки есть предел 4096 байт; предусмотрен режим пропуска слишком длинной строки до терминатора. На сервере тоже есть проверка размера накопленного буфера с порогом 32 КиБ. Последнюю не следует принимать за строгую проверку длины любой готовой строки: поиск LF в текущей реализации выполняется раньше проверки размера.

## Как устроен клиент Symbian

В приложении используется обычный для этого проекта каркас Avkon:

```text
CTgPagerApplication
    └─ CTgPagerDocument
           └─ CTgPagerAppUi
                  ├─ CTgPagerAppView
                  ├─ CTgSettings
                  └─ CTgEngine
                         ├─ CTgPollConn
                         └─ CTgSendConn
```

`Application` и `Document` создают приложение и его UI. Основная прикладная логика распределена между следующими классами:

| Класс | Ответственность |
| --- | --- |
| `CTgPagerAppUi` | Команды меню, диалоги, применение настроек, реакция на события движка |
| `CTgPagerAppView` | Список сообщений, отметки времени, перенос текста и ограничение истории |
| `CTgSettings` | Загрузка и сохранение адреса, порта и кода доступа |
| `CTgEngine` | Управление соединениями, передача событий UI, отложенная отправка |
| `CTgConn` | Общая логика DNS, подключения, авторизации, чтения, записи и таймера |
| `CTgPollConn` | Цикл `POLL`, приём сообщений и переподключение |
| `CTgSendConn` | Отправка одного сообщения через отдельное соединение |

Движок уведомляет интерфейс через `MTgUiObserver::HandleTgEvent()`. Среди событий есть подключение, потеря связи, неверный код доступа, ошибка отправки и входящее сообщение. Поэтому сетевой код не создаёт диалоги и не управляет списком напрямую.

### Сеть через active objects

`CTgConn` наследуется от `CActive`. Вместо отдельного потока под каждое соединение телефон использует асинхронные запросы и active scheduler.

Последовательность операции следующая:

1. Код запускает асинхронный запрос, передавая `iStatus`.
2. Вызывает `SetActive()` и возвращает управление планировщику.
3. После завершения запроса планировщик вызывает `RunL()`.
4. `RunL()` проверяет результат и выбирает следующий шаг по текущему состоянию.

Основной путь подключения можно представить так:

```text
EIdle
  │
  ├─ указан IP ───────────────────┐
  │                              │
  └─ указано имя → EResolve ──────┤
                                 ↓
                              EConnect
                                 ↓
                               EAuthW
                                 ↓
                        чтение ответа AUTH
                                 ↓ OK
                         запись POLL / SEND
                                 ↓
                            чтение ответа
```

Для доменного имени используется `RHostResolver`, для TCP — `RSocket`, для повторной попытки — `RTimer`. Общая сессия socket server хранится в `CTgEngine` как `RSocketServ`.

Сложность этой модели — в согласованности состояний и отмены. Нужно знать, какая операция сейчас активна, что отменять при отключении и можно ли уже начинать новую запись. Метод `DoCancel()` отдельно обрабатывает DNS, таймер и сокет. Попытка запустить операцию поверх активной возвращает `KErrInUse`.

Ожидание сети само по себе не должно занимать UI-поток синхронным чтением. Но обработчики `RunL()` всё равно должны быстро возвращать управление: active objects не превращают длительный вычислительный код в фоновую работу.

### Память, дескрипторы и Leave

Клиент написан с использованием дескрипторов Symbian: `TBuf`, `TBuf8`, `TDesC`, `TPtrC`. У буфера задана ёмкость, поэтому длина строки становится частью проектирования.

Некоторые размеры из исходников:

| Данные | Буфер |
| --- | --- |
| Адрес сервера | `TBuf<64>` |
| Код доступа | `TBuf<32>` |
| Фрагмент чтения TCP | `TBuf8<1024>` |
| Накопленная строка протокола | `TBuf8<4096>` |
| Буфер записи соединения | `TBuf8<4096>` |
| Команда исходящего сообщения | `TBuf8<2048>` |
| Декодированный входящий текст | `TBuf16<600>` |

В кодировщике проверяется оставшаяся ёмкость перед добавлением байтов. Это необходимо: 200 единиц UTF-16 не равны 200 байтам UTF-8, а экранирование тоже увеличивает размер.

Создание объектов выполняется через `new (ELeave)`, фабрики `NewL()` и двухфазную конструкцию. Во время потенциально прерываемой инициализации объект помещается на `CleanupStack`. После успешного `ConstructL()` его снимают со стека.

Например, так создаётся движок:

```cpp
CTgEngine* CTgEngine::NewL(MTgUiObserver& aUi)
    {
    CTgEngine* self = new (ELeave) CTgEngine(aUi);
    CleanupStack::PushL(self);
    self->ConstructL();
    CleanupStack::Pop(self);
    return self;
    }
```

UI перехватывает часть таких выходов через `TRAPD`. Это ещё одна обязанность при работе со старым C++-окружением: учитывать модель управления ресурсами платформы при создании каждого диалога, списка и сетевого объекта.

## Как устроен Python-прокси

Вся серверная реализация находится в одном файле на 482 строки. Внешних Python-зависимостей нет: используются `socket`, `threading`, `collections`, `urllib.request`, `json`, `logging`, `signal` и другие модули стандартной библиотеки.

Сервер разделён на три исполняемые части:

- Главный поток принимает TCP-соединения.
- Фоновый `telegram_worker()` забирает обновления Telegram.
- Для каждого TCP-клиента создаётся поток `handle_client()`.

Потоковая модель здесь позволяет использовать блокирующие API. Пока один клиент ждёт сообщение, другой может отправить текст, а фоновый поток — получить очередное обновление.

### Очередь между Telegram и телефоном

Тексты хранятся в общей очереди:

```python
_queue = collections.deque(maxlen=100)
_cond = threading.Condition()
```

Поток Telegram собирает подходящие сообщения из одного ответа `getUpdates`, кладёт пакет в очередь под блокировкой и вызывает `notify_all()`.

Обработчик `POLL` проверяет очередь под той же блокировкой. Если она пуста, ждёт через `Condition.wait()`. На время ожидания блокировка освобождается, поэтому Telegram-поток может добавить новые тексты.

При получении данных обработчик забирает накопленный пакет, очищает общую очередь и отправляет строки `MSG`, а затем `END`.

Это очередь с конкурирующими потребителями: один пакет получает один обработчик `POLL`. Несколько подключённых телефонов не получат одинаковую копию сообщения. Отдельных пользователей, персональных очередей и широковещательной доставки здесь нет.

При переполнении `deque` вытесняет старые сообщения, сервер пишет об этом в лог. Максимум в 100 текстов ограничивает память ценой возможной потери непрочитанного.

### Два long polling работают одновременно

В проекте есть два независимых длительных ожидания:

```text
Telegram ── getUpdates(timeout=25) ──► очередь прокси
                                               │
                                               └── POLL, до 50 с ──► Nokia
```

Они выполняются параллельно. Если сообщение появляется во время ожидания, серверный поток кладёт его в очередь и будит обработчик телефона. Поэтому 25 и 50 секунд не нужно складывать в обязательную задержку 75 секунд: это пределы ожидания без новых данных.

У сетевых вызовов отдельно заданы таймауты:

| Операция | Значение в коде |
| --- | --- |
| Long polling Telegram | 25 с |
| HTTP-запрос `getUpdates`, включая запас на сеть | 40 с |
| Ожидание данных внутри телефонного `POLL` | До 50 с |
| Проверка состояния ожидающего клиента | С интервалом ожидания до 5 с |
| Таймаут операций клиентского сокета на прокси | 120 с |
| HTTP-запрос `sendMessage` | 15 с |
| Повтор подключения приёмного канала на телефоне | Через 10 с после обрабатываемой ошибки |
| Максимальная пауза между повторами `getUpdates` | 60 с |

На практике задержка ещё зависит от мобильной сети, состояния соединения и обработки событий телефоном. Из этих констант нельзя получить измеренное время доставки или расход батареи.

### Как прокси читает Telegram

`telegram_worker()` вызывает `getUpdates` с `allowed_updates=["message"]`. Из обновлений выбираются непустые `message.text`. Нетекстовые сообщения и команды, начинающиеся с `/`, отбрасываются.

После обработки обновления вычисляется `offset = update_id + 1`. Этот offset передаётся в следующем запросе. Согласно [описанию `getUpdates`](https://core.telegram.org/bots/api#getupdates), запрос с большим offset подтверждает предыдущие обновления. Там же указано, что метод не работает при установленном webhook; автоматически удалять webhook этот прокси не пытается.

Для исходящего текста вызывается `sendMessage`: без `parse_mode`, с отключённым предпросмотром ссылок. Телефонные сообщения не интерпретируются сервером как Markdown или HTML.

При ошибках `getUpdates` используется нарастающая пауза: 1, 2, 4 секунды и далее до 60 секунд. После успеха она сбрасывается. Для HTTP 429 код пытается прочитать `retry_after`, также ограничивая фактическую паузу 60 секундами.

У отправки другая семантика: неудачный `sendMessage` возвращает телефону `ERR telegram`. Автоматического повтора этой операции в сервере нет.

## Трудность № 1: собрать приложение инструментами другой эпохи

Клиент привязан к конкретной среде Windows:

```text
SDK:          C:\Symbian\8.1a\S60_2nd_FP3
Perl:         ActivePerl 5.6.1 в C:\Perl
Цель сборки:  thumb urel
```

В репозитории есть `TgPager/build.cmd`, который выставляет `EPOCROOT`, подготавливает `PATH` и запускает цепочку:

```bat
bldmake bldfiles
abld.bat build thumb urel
makesis.exe tgpager.pkg
```

Первый шаг создаёт файлы сборочной системы. Второй собирает приложение для устройства в release-конфигурации. Третий упаковывает приложение и ресурсы в SIS.

Здесь важны детали, которые в современном проекте легко принять за случайность.

**Perl должен стоять первым в `PATH`.** По инструкциям проекта инструменты SDK требуют именно локальную ActivePerl 5.6.1. Подмена другим Perl ломает эту сборочную цепочку. Поэтому скрипт явно добавляет `C:\Perl\bin` перед остальными путями.

**Пути привязаны к диску C:.** В `build.cmd` прописан абсолютный `PRJ`, а инструкция требует путь без пробелов на этом диске. При переносе репозитория нужно исправлять и `PRJ`, и путь копирования готового SIS в конце скрипта.

**Результаты сборки находятся внутри SDK.** Исполняемый модуль попадает в:

```text
C:\Symbian\8.1a\S60_2nd_FP3\Epoc32\Release\THUMB\UREL\
```

Ресурсы и AIF — в:

```text
C:\Symbian\8.1a\S60_2nd_FP3\Epoc32\Data\Z\System\Apps\tgpager\
```

Файл `sis/tgpager.pkg` ссылается именно на эти абсолютные пути. Копирования одного каталога проекта на другую машину для воспроизводимой сборки недостаточно.

**Эмуляторная сборка в описанном окружении недоступна.** Для `winscw` нет нужного VC6/CodeWarrior. Доступен путь сборки для устройства, поэтому проверку установки, отображения и поведения мобильной сети нужно проводить на телефоне.

Это ограничение конкретной подготовленной среды. Оно не доказывает невозможность собрать эмуляторный вариант в другом окружении.

В репозитории сохранён SIS размером 11 907 байт — примерно 11,6 КиБ. Это размер установочного файла, а не потребление оперативной памяти приложением. Наличие бинарника также не заменяет повторную сборку исходников.

## Трудность № 2: UID должен совпасть в четырёх местах

У TgPager выбран UID3 `0x70000072`. Он указан в четырёх файлах:

| Файл | Где используется UID |
| --- | --- |
| `group/tgpager.mmp` | Параметры собираемого приложения |
| `sis/tgpager.pkg` | Метаданные пакета установки |
| `src/tgpagerapplication.cpp` | `KUidTgPagerApp`, возвращаемый приложением |
| `aif/tgpageraif.rss` | `app_uid` для AIF |

По инструкции проекта локальный `makesis` разбирает это значение как знаковое, поэтому UID должен оставаться меньше `0x80000000`.

При изменении идентификатора приходится синхронно менять все четыре места. Сборщик, упаковщик и оболочка телефона получают сведения о приложении из разных файлов; одной общей константы для них здесь нет.

SIS устанавливает `.app`, основной `.rsc`, ресурс названия `TgPager_caption.rsc` и `.aif` в каталог `\system\apps\TgPager` на выбранном диске. В описанном для проекта сценарии S60 2nd Edition дополнительная подпись SIS не требуется; переносить эту инструкцию на другие поколения Symbian без проверки нельзя.

## Трудность № 3: кириллица работает в программе, но мешает сборке ресурсов

Одна из самых характерных проблем проекта — разные возможности самой платформы и её инструментов сборки.

Приложение работает с UTF-16 и может показывать русские строки. Но используемый компилятор ресурсов SDK не принимает UTF-8-исходники ресурсов с кириллицей. По этой причине в `data/*.rss` и `.loc` оставлены ASCII-строки.

Например, пункт меню в `.rss` объявлен так:

```text
MENU_ITEM
    {
    command = ETgPagerCmdWrite;
    txt = "Write";
    }
```

Русские надписи находятся в `inc/tgstrings.h` как последовательности UTF-16-кодовых единиц:

```cpp
static const TText KStMe[] = {0x042F, 0};                 // Я
static const TText KStBot[] = {0x0411, 0x043E, 0x0442, 0}; // Бот

#define TGSTR(s) TPtrC(s)
```

Во время выполнения `DynInitMenuPaneL()` заменяет подписи пунктов меню:

```cpp
aMenuPane->SetItemTextL(ETgPagerCmdWrite, TGSTR(KStWrite));
aMenuPane->SetItemTextL(ETgPagerCmdConnect, TGSTR(KStConnect));
```

Подсказки диалогов задаются через `SetPromptL()` тем же способом. Имя приложения оставлено латиницей — `TG Pager`.

Так сборка ресурсов получает понятный ей ASCII, а экранные строки создаются в C++ как UTF-16. Обход усложняет сопровождение: добавить новый русский текст теперь означает обновить массив кодовых единиц и нужное место подстановки.

Эта проблема показывает, почему наличие Unicode в ОС ещё не гарантирует, что весь путь от исходника до интерфейса одинаково понимает кодировки.

## Трудность № 4: UTF-8, UTF-16 и «400 символов» — разные ограничения

На сервере текст представлен Python-строкой, на проводе — UTF-8, на телефоне — 16-битными дескрипторами. Преобразования реализованы в `inc/tgutf.h`.

Для обычной кириллицы преобразование сравнительно прямое: одна кодовая единица UTF-16 превращается в два байта UTF-8. Символы вне основной многоязычной плоскости требуют другого пути: суррогатная пара UTF-16 собирается в одну кодовую точку и кодируется четырьмя байтами UTF-8. При приёме выполняется обратное преобразование.

В коде есть обработка суррогатных пар, но транспортная поддержка emoji не добавляет соответствующие глифы в шрифт N70. Передать символ и показать его на экране — две разные задачи.

Кроме того, лимиты считаются в разных единицах:

- `TBuf<200>` ограничивает исходящий текст 200 кодовыми единицами UTF-16. Символ вне BMP занимает две единицы.
- `text[:MAX_TEXT]` на сервере ограничивает Python-строку кодовыми точками.
- `TBuf8` ограничивает число байтов, включая результат кодирования и экранирования.

Из этого следует конкретный пограничный случай. Сервер может пропустить 400 символов вне BMP, которым потребуется 800 кодовых единиц UTF-16. Клиент декодирует входящий текст в `TBuf16<600>`, поэтому весь такой текст не поместится. Декодер умеет сообщать об усечении, но вызывающий код при приёме этот результат не использует.

Поэтому формулировка «входящие до 400 символов» точно описывает серверный лимит, но не гарантирует показ любого сочетания из 400 Unicode-символов на телефоне.

Преобразователь также не стоит воспринимать как полностью проверенный универсальный валидатор UTF-8: в репозитории нет набора тестов на все некорректные последовательности. Его назначение здесь — обмен короткими текстами между конкретными двумя реализациями.

Есть и отдельная практическая деталь: путь кодирования текста сообщения не используется для кода доступа. В `AUTH` и конфигурационном файле выполняется простое преобразование между 16- и 8-битными дескрипторами. Для адреса и кода доступа в текущей версии следует использовать ASCII; поддержку кириллицы в сообщениях нельзя автоматически переносить на эти поля.

## Трудность № 5: сообщения приходили, но список показывал пустоту

У этой ошибки сохранилось конкретное исправление в Git — коммит `1c47171` с сообщением `empty messages`.

Для отображения истории используется `CAknSingleStyleListBox`. Текст элемента такого списка имеет внутренний формат с полями, разделёнными табуляцией. В используемом здесь варианте перед отображаемым текстом нужен `\t`.

Раньше код добавлял обычный текст строки. Исправление добавило подготовку:

```cpp
line.Zero();
line.Append('\t');
```

После неё дописывается текст элемента. Строка в модели имеет вид:

```text
\t[12:34] Бот: Проверка связи
```

Здесь `\t` обозначает один настоящий символ табуляции в памяти.

Согласно комментарию в исправлении, без разделителя текст не отображался и элементы выглядели пустыми. Это ошибка на границе модели данных и UI-компонента: даже правильная строка сообщения должна быть упакована в ожидаемый списком формат.

В том же коммите ширину ручного переноса уменьшили с 30 до 26, а верхнюю status pane скрыли, чтобы освободить место для истории.

Сейчас перенос реализован простым алгоритмом: ищется пробел в пределах доступной длины, а если его нет — берётся фрагмент по лимиту. Продолжения получают отступ. Это перенос по числу кодовых единиц, без измерения реальной ширины глифов.

История ограничена **120 элементами списка**. Одно длинное сообщение занимает несколько элементов, поэтому это не лимит в 120 сообщений. При переполнении удаляются верхние элементы; начало старого сообщения тоже может исчезнуть отдельно от его продолжения.

В истории показывается локальное время добавления текста на телефоне. Сервер передаёт только текст, без Telegram timestamp. Если сообщение ждало в очереди, отметка на экране соответствует моменту его получения приложением.

## Трудность № 6: обрыв связи меняет смысл «доставлено»

Телефонный приёмный канал различает неверный код доступа и обычную сетевую ошибку.

При ошибке авторизации он прекращает попытки и передаёт UI событие о неверном коде. При обрабатываемой сетевой ошибке сообщает о потере связи и ставит `RTimer` на 10 секунд, после чего пытается подключиться снова. Отключение пользователем отменяет ожидание.

Интерфейс хранит `iWasConnected` и `iDownShown`: это позволяет показать потерю соединения или недоступность сервера, не добавляя одинаковую запись на каждой неудачной попытке.

На сервере есть отдельная проблема: телефон может исчезнуть, пока его `POLL` ждёт сообщения. Если затем отдать этому обработчику всю очередь, сообщение может уйти в уже закрытый канал.

В `handle_poll()` предусмотрены проверки закрытия соединения через `select()` и `recv()` с `MSG_PEEK`. Если обнаружено, что клиент ушёл, выбранные сообщения возвращаются в очередь. При ошибке записи туда возвращается остаток пакета, который сервер ещё не успел успешно записать в сокет.

Это полезная защита, но она не даёт гарантии прочтения приложением. Успешный `sendall()` означает, что локальный сетевой стек принял байты. Он не подтверждает, что Nokia получила строку, декодировала её и добавила в список.

В протоколе нет идентификаторов сообщений и подтверждения от телефона. В результате остаются несколько окон неопределённости:

- Прокси мог записать `MSG` в сокет, после чего связь оборвалась до обработки сообщения телефоном.
- Telegram мог принять исходящий текст, а ответ `OK` не дошёл до Nokia. Повторная отправка пользователем способна создать дубль.
- Прокси мог подтвердить обновления Telegram через offset, затем потерять ещё не отданную телефону очередь при перезапуске.

Очередь, offset и автоматически выбранный получатель хранятся только в памяти процесса. Для более строгих гарантий пришлось бы добавлять хранение на диске, идентификаторы, клиентские подтверждения и правила повторной доставки. Это уже затронуло бы и сервер, и телефонный протокол.

Другая граница надёжности — зависание без явной ошибки. На сервере таймауты сетевых операций заданы явно. В клиенте `RTimer` используется для пауз между попытками, но отдельного прикладного таймера, который ограничивал бы каждый DNS-запрос, connect или чтение, нет. Обещать обнаружение любого обрыва ровно через 10 секунд было бы неверно: 10 секунд — пауза после уже обработанной ошибки.

## Трудность № 7: очередь отправки оказалась одним слотом

У телефона нет полноценной очереди исходящих сообщений. Если `CTgSendConn` занят, движок сохраняет следующий текст в:

```cpp
TBuf16<200> iPending;
TBool iPendingValid;
```

После завершения текущей отправки `FlushPending()` пытается отправить сохранённый текст.

Здесь существенна ёмкость именно в одно сообщение. Если во время отправки A пользователь создаст B, а затем C, текст C перезапишет B в `iPending`. Это следует из реализации `CTgEngine::Send()`.

UI тоже не хранит состояние доставки у каждой записи. Он добавляет строку `Я: ...` в историю **до** вызова сетевой отправки. При ошибке появляется отдельная системная запись «Не отправлено», но исходная строка не получает собственного статуса.

Поэтому наличие текста в истории означает, что пользователь его ввёл. Для надёжного исходящего буфера понадобились бы отдельные записи с состоянием, очередь и определённая политика повторов. Текущий слот лишь позволяет отложить один текст, пока канал занят.

## Трудность № 8: выбрать собеседника и действительно ограничить доступ

Прокси должен знать, в какой чат отправлять тексты телефона. Для этого предусмотрен `ALLOWED_CHAT_ID`.

Если значение задано, оно используется как получатель, а сообщения из других чатов отбрасываются. Если значение отсутствует, первый подходящий текст фиксирует `target_chat_id`. Команда `/start` для этого не подходит: сообщения, начинающиеся с `/`, фильтруются раньше.

До выбора получателя `SEND` возвращает `ERR nochat`.

У автоматического режима есть расхождение между ожидаемым ограничением и фактическим кодом. После выбора `target_chat_id` прокси продолжает принимать входящие тексты из других чатов. Проверка чужого `chat_id` выполняется только при явно заданном `ALLOWED_CHAT_ID`.

Проверка функции `process_update()` на двух искусственных сообщениях без обращений к Telegram даёт такой результат:

```text
Первое сообщение: chat_id=101 → текст принят
Второе сообщение: chat_id=202 → текст тоже принят
Получатель исходящих: target_chat_id=101
```

То есть телефон может увидеть текст второго собеседника, но ответит в первый чат. В текущем коде фиксация получателя не означает фильтрацию всех последующих входящих по этому получателю.

Для сценария с одним собеседником уже существующий явный `ALLOWED_CHAT_ID` устраняет эту неоднозначность. А изменение автоматического режима потребовало бы отдельной проверки кода. В статье важно оставить этот момент видимым: комментарий о «первом написавшем» ещё не доказывает нужную политику доступа.

## Настройки и жизненный цикл сервера

На телефоне конфигурация состоит из трёх строк: адрес, порт, код доступа. Она загружается при запуске; при сохранённом адресе сразу начинается подключение. После изменения настроек UI сохраняет их, останавливает приёмный канал, применяет новые значения и запускает подключение заново.

Путь конфигурации заслуживает отдельной проверки на устройстве. README указывает файл рядом с приложением, но в коде имя задано как `"\\tgp.cfg"` и объединяется с каталогом через `TParse`. Начальный обратный слеш задаёт корневой путь. Поэтому обещать по README, что файл точно находится в `\system\apps\TgPager`, без проверки разрешённого пути нельзя.

История сообщений на диск не сохраняется. Она живёт в модели списка и теряется после закрытия приложения.

Сервер настраивается через окружение:

| Переменная | Назначение | По умолчанию |
| --- | --- | --- |
| `BOT_TOKEN` | Токен Telegram-бота | Обязателен |
| `LISTEN_HOST` | Адрес привязки TCP-сервера | `0.0.0.0` |
| `LISTEN_PORT` | TCP-порт | `7777` |
| `REQUIRE_CODE` | Общий код доступа | Пустой |
| `ALLOWED_CHAT_ID` | Разрешённый Telegram-чат и получатель | Не задан |
| `MAX_TEXT` | Серверный лимит текста в обе стороны | `400` |
| `TG_API_BASE` | Адрес Bot API, в том числе локальной подмены для проверки | `https://api.telegram.org` |

При `SIGTERM` или `SIGINT` выставляется общий `shutdown`, закрываются слушающий и клиентские сокеты. Главный цикл перестаёт принимать подключения и ограниченное время ждёт потоки. Паузы повторов реализованы через `shutdown.wait()`, поэтому остановка может прервать такую паузу.

При этом поток HTTP может ещё ждать завершения `urlopen()`; ожидание worker при остановке ограничено двумя секундами, а сам поток daemon. Здесь реализовано ограниченное по времени завершение процесса, без обещания обязательно закончить все операции и доставить всю очередь.

Для запуска предусмотрен сценарий systemd. В `server-prompt.md` перечислены требования к unit: ожидание сети, автоматический перезапуск, отдельный пользователь или `DynamicUser`, ограничения прав и файловой системы. Готового `.service` в репозитории нет — это требования к развёртыванию, а не уже поставляемый конфигурационный файл.

Сервер также пока ориентирован на небольшой личный сценарий. Поток создаётся на каждое подключение; явного лимита активных потоков нет. Список `_client_threads` сохраняет и завершённые потоки. При длительной работе с многочисленными короткими подключениями этот список растёт. Ограниченная очередь сообщений сама по себе не ограничивает все ресурсы процесса.

## Как проверять систему, когда полный цикл зависит от телефона

В репозитории нет автоматических тестов и CI. Проверка делится по границам компонентов: сборка клиента, протокол прокси и поведение на устройстве.

Для клиента предусмотрен запуск `TgPager\build.cmd` в подготовленной Windows-среде. После успешной сборки SIS переносится на телефон через Bluetooth или PC Suite и устанавливается. На устройстве нужно проверить ввод, отображение, уведомления и восстановление связи: компиляция эти свойства не подтверждает.

Для сервера полезен `TG_API_BASE`. Можно направить запросы в локальную подмену Bot API, которая отдаёт заданные ответы `getUpdates` и фиксирует вызовы `sendMessage`. Сам mock-сервер в репозитории не поставляется, но точка подмены в коде есть. Она позволяет проверять прокси без реального токена и переписки.

После запуска прокси протокол можно проверить через `nc`:

```sh
nc 127.0.0.1 7777
```

Затем ввести команды, согласованные с конфигурацией сервера:

```text
AUTH example-code
SEND Проверка кириллицы
```

Для проверки приёма во втором соединении:

```text
AUTH example-code
POLL
```

Это ручные действия для локального стенда. `SEND` с ответом `OK` требует известного получателя и успешного ответа API; одного работающего TCP-сокета недостаточно.

Набор существенных сценариев получается таким:

| Проверка | Что должно быть видно |
| --- | --- |
| Неверный код доступа | `ERR auth` и закрытие соединения |
| `SEND` без известного получателя | `ERR nochat` |
| Входящий текст | `MSG ...`, затем `END` |
| Пустая очередь | Ожидание, затем `END`, с сохранением соединения |
| Кириллица, обратный слеш, перевод строки | Согласованное кодирование и экранирование в обе стороны |
| Одна команда в нескольких TCP-записях | Сборка полной строки перед обработкой |
| Несколько команд в одной TCP-записи | Последовательная обработка всех строк |
| Закрытие телефона во время `POLL` | Проверка возврата ещё не записанных сообщений в очередь |
| Два конкурирующих `POLL` | Пакет получает один обработчик |
| Переполнение очереди | Вытеснение старых текстов и запись в лог |
| Несколько отправок при занятом канале | Наблюдаемое поведение одного `iPending` |
| Два разных Telegram-чата | Различие явного `ALLOWED_CHAT_ID` и автоматического выбора |
| Остановка и перезапуск прокси | Потеря состояния в памяти и восстановление соединения телефоном |

Эта таблица описывает проверяемое поведение и границы реализации. Она не является отчётом о прохождении всех сценариев. При подготовке статьи исходники были разобраны, а приём сообщений из двух чатов проверен отдельно на `process_update()`; сборка Windows-клиента и проверка на N70 заново не выполнялись.

## Что этот проект показывает о работе с LLM-кодом

В репозитории есть полезный артефакт — `server-prompt.md`. Это подробное задание для генерации серверной части: команды, ответы, экранирование, таймауты, ограничение очереди и сценарии проверки.

Такой документ делает границу двух компонентов явной. Сервер и клиент могут быть написаны раздельно, но должны одинаково понимать пустой `AUTH`, конец ответа `POLL`, обратный слеш и ошибку отсутствующего получателя. Произвольное изменение одной стороны сломает обмен.

При этом даже подробное задание не подменяет чтение реализации. В текущем проекте особенно показательны три места:

- В описании фигурирует фиксация первого собеседника, а фильтрация остальных входящих в автоматическом режиме отсутствует.
- Поддержка Unicode есть в кодировщике, но ёмкости UTF-16-буферов и шрифты отдельно ограничивают результат.
- Текст появляется в истории до подтверждения отправки, а буфер ожидающих сообщений вмещает только один текст.

Исправление пустых строк списка показывает ещё одну границу: исходник может успешно собираться и получать данные, но визуальный компонент требует собственного формата модели. Проверка такого поведения остаётся частью работы на целевой платформе.

В TgPager путь одного сообщения проходит через несколько поколений технологий: Telegram Bot API, Python, TCP, active objects Symbian и список Avkon. На каждом переходе обнаруживается своё условие: собрать полную строку, правильно преобразовать кодировку, дождаться завершения операции, добавить нужный разделитель в модель списка. Даже у маленького пейджера хватает мест, где данные могут потеряться или стать невидимыми.

LLM-агент написал код, но оценивать результат приходится по всей этой цепочке. Успешная сборка ещё оставляет вопросы: появился ли текст на экране, куда ушёл ответ, что случилось после обрыва связи. Старый телефон делает эти вопросы особенно наглядными.

У проекта остаются вполне конкретные продолжения: очередь исходящих, подтверждения доставки, сохранение истории. Но уже нынешняя версия даёт N70 простую задачу, для которой достаточно её экрана и клавиатуры: получить сообщение из Telegram и позволить набрать ответ. Спустя двадцать лет этим кнопкам снова нашлась работа.
