Symbian 8.1: истоки 

Архитектура Symbian OS 8.1 возникла не с нуля. Её основой стала операционная система EPOC, разработанная британской компанией Psion для карманных компьютеров и электронных органайзеров в 1980–1990-х годах. 



Особенно большое влияние на Symbian оказали устройства семейства Psion Series 5, работавшие под управлением EPOC32. Именно от этой системы Symbian унаследовала значительную часть архитектурных принципов, программных интерфейсов и инструментов разработки. 

Наиболее интересна преемственность не внешнего вида устройств, а программных интерфейсов.

Эти механизмы существовали задолго до Symbian OS 8.1. Архитектура EPOC32 уже в 1997 году включала микроядерный подход, системные серверы, файловую подсистему, оконный сервер и объектно-ориентированные библиотеки. 

Важно отметить, что EPOC16 и EPOC32 — разные кодовые базы. От Psion Series 3 система унаследовала прежде всего идеи и традицию разработки, тогда как непосредственным техническим предшественником Symbian OS 8.1 стала EPOC32 устройств Series 5 и 5mx.

Архитектура ОС

Архитектура Symbian 8.1 построена по многослойному принципу. Основным языком разработки был C++ (C++98 с характерными идиомами Symbian), дополненный специфическими механизмами управления памятью, обработки событий и взаимодействия с системными службами.

Про внутренности N70 не вижу смысла подробно растекаться, так как на Хабре это недавно описал monobogdan в этой замечательной статье.



В Symbian 8.1 существовали варианты с ядрами EKA1 и EKA2, поэтому некоторые низкоуровневые особенности зависели от конкретного устройства.

В классической модели GUI-приложений Symbian C++ используются несколько основных компонентов:





Application (CApaApplication) — описывает приложение и создаёт объект документа.



Document (CApaDocument) — управляет моделью данных приложения.



AppUi (CAknAppUi или CEikAppUi) — обрабатывает команды пользователя и управляет интерфейсом.



View/Container (CCoeControl) — отображает элементы интерфейса и обрабатывает события управления.

Конкретные классы зависят от платформы пользовательского интерфейса. Например, S60 использует Avkon, а UIQ — собственный UI-фреймворк. Поэтому приложение для S60 не обязательно совместимо с UIQ, даже если оба устройства работают под Symbian OS 8.1.



Для работы с памятью используются классы с соглашениями об именовании C, R, T и M. Например, классы категории C обычно наследуются от CBase, а классы категории R часто представляют ресурсы, которые необходимо явно закрывать.

Вместо обычной обработки исключений C++ применяется механизм Leave, а для безопасной очистки объектов при ошибках — Cleanup Stack.



Одна из важнейших особенностей Symbian — механизм Active Objects. Он позволяет выполнять асинхронные операции без создания отдельного потока для каждой задачи. Например, приложение может отправить запрос на чтение файла или получение данных по сети, продолжить обработку других событий и получить уведомление после завершения операции.

Основные элементы этой модели — CActive, CActiveScheduler и методы RunL(), DoCancel(). Такой подход снижает потребление памяти и особенно полезен на мобильных устройствах. Вообще, про это можно и дальше рассказывать, но вышесказанного нам хватит чтобы написать простой Hello World.

Настраиваем SDK

Важные требования к установке, пришедшие из 2004 года: 

Путь к SDK — без пробеловC:\Symbian\8.1a\S60_2nd_FP3

Perl 5.6.1 должен быть первым в PATH — любой современный Perl (5.30+) ломает скрипты сборки.

Переменная окружения EPOCROOT в каноническом формате: \Symbian\8.1a\S60_2nd_FP3\ — без буквы диска, с ведущим и замыкающим слэшем. Инструменты сами подставляют букву текущего диска.

Проект должен лежать на том же диске, что и SDK, и тоже без пробелов в пути.

$env:EPOCROOT = '\Symbian\8.1a\S60_2nd_FP3\'
$env:PATH = "C:\Perl\bin;C:\Symbian\8.1a\S60_2nd_FP3\Epoc32\gcc\bin;C:\Symbian\8.1a\S60_2nd_FP3\Epoc32\tools;$env:PATH"

Важный момент, о котором обычно умалчивают мануалы: оригинальный SDK распространялся как .exe-установщик, который сам прописывал все переменные окружения. Zip с archive.org — это просто распакованное дерево каталогов: инструменты в нём есть, но система про них не знает, а инструменты не знают, где сами находятся. «Установил SDK» и «SDK работает» — две большие разницы; между ними — четыре настройки выше.

Разбирая содержимое SDK, я обнаружил в Epoc32\gcc\bin полноценный кросс-компилятор GNU. А команда bldmake plat (встроенная справка по платформам) честно показывает привязку таргетов к компиляторам:



Ниже THUMB

Расшифровка: сборка под реальное железо (armi/thumb) идёт через GNU GCC, который лежит прямо в SDK. Старые коммерческие компиляторы нужны только для таргетов эмулятора (wins/winscw). То есть цикл «написал → собрал → поставил на телефон» полностью замкнут бесплатными средствами из коробки — нужно только уметь пользоваться командной строкой. Пояснение по таргетам ARM: 





ARMI — интерворкинг-таргет, бинарник совместим и с ARM и с THUMB-кодом (рекомендовался для дистрибуции)



ARM4 — чистый 32-битный ARM (быстрее, толще)



THUMB — 16-битные инструкции (компактнее, чуть медленнее) — дефолт в pkg-шаблонах Nokia.



Забавная деталь эпохи: GCC здесь выдаёт бинарники в формате PE (Portable Executable, формат Windows DLL), которые затем пропускаются через PETRAN — постпроцессор Symbian, преобразующий PE-контейнеры в E32-образ (формат исполняемых файлов Symbian EKA1). 

Архитектура Symbian-приложения

Symbian 8.1 — это EKA1, микроядерная архитектура с клиент-серверной моделью: любой доступ к железу и системным сервисам — через серверы (Window Server, File Server, Font&Bitmap Server). Приложение — обычный E32-модуль с точкой входа E32Dll (да, приложение формально является DLL).

Ключевые идиомы Symbian C++, без которых код не соберётся и не заработает:





Two-phase construction: конструктор C++ не может оставить (Leave — местный аналог исключений), поэтому вся оставляющая инициализация — в ConstructL();

Дескрипторы (TBuf, HBufC, TPtrC) вместо char* — строки с длиной в первом байте, 8- и 16-битные.

Весь интерфейс описывается декларативно в .rss-файлах (RSG-компилятор превращает их в бинарные .rsc и заголовки с ID). Строки вынесены в .loc

Пишем пейджер для Telegram

У Nokia N70 всё ещё есть экран, клавиатура и возможность установить нативное приложение. Для коротких сообщений этого достаточно. Проблемы начинаются, когда на другом конце соединения оказывается современный сервис с HTTPS, JSON и постоянно меняющимся API.

TgPager связывает эти два мира: на телефоне работает небольшое приложение для Symbian, на сервере — Python-прокси, а собеседник пишет обычному Telegram-боту. Сообщение появляется на Nokia; ответ можно набрать с её клавиатуры. Получается двусторонний пейджер.





Публичный Telegram Bot API требует HTTPS. В этой реализации клиент на N70 использует обычный TCP и не решает задачу совместимости старого TLS-стека с современным сервисом. Эту обязанность выполняет серверная urllib.request.

Немного деталей прокси (серверная python-часть)

Вся серверная реализация находится в одном файле на 482 строки. Внешних Python-зависимостей нет: используются socket, threading, collections, urllib.request, json, logging, signal и другие модули стандартной библиотеки.

Сервер разделён на три исполняемые части:





Главный поток принимает TCP-соединения





Фоновый telegram_worker() забирает обновления Telegram





Для каждого TCP-клиента создаётся поток handle_client()



Поток Telegram собирает подходящие сообщения из одного ответа getUpdates, кладёт пакет в очередь под блокировкой и вызывает notify_all().Обработчик POLL проверяет очередь под той же блокировкой. Если она пуста, ждёт через Condition.wait(). 

На время ожидания блокировка освобождается, поэтому Telegram-поток может добавить новые тексты.При получении данных обработчик забирает накопленный пакет, очищает общую очередь и отправляет строки MSG, а затем END.

Это очередь с конкурирующими потребителями: один пакет получает один обработчик POLL. Несколько подключённых телефонов не получат одинаковую копию сообщения. Отдельных пользователей, персональных очередей и широковещательной доставки здесь нет.

Клиент на N70

Клиент написан с использованием дескрипторов Symbian: TBuf, TBuf8, TDesC, TPtrC. У буфера задана ёмкость, поэтому длина строки становится частью проектирования.

В кодировщике проверяется оставшаяся ёмкость перед добавлением байтов. Это необходимо: 200 единиц UTF-16 не равны 200 байтам UTF-8, а экранирование тоже увеличивает размер.

Основной путь подключения можно представить так:



Для доменного имени используется RHostResolver, для TCP — RSocket, для повторной попытки — RTimer. Общая сессия socket server хранится в CTgEngine как RSocketServ.

Сложность этой модели — в согласованности состояний и отмены. Нужно знать, какая операция сейчас активна, что отменять при отключении и можно ли уже начинать новую запись. Метод DoCancel() отдельно обрабатывает DNS, таймер и сокет. Попытка запустить операцию поверх активной возвращает KErrInUse.

Ожидание сети само по себе не должно занимать UI-поток синхронным чтением. Но обработчики RunL() всё равно должны быстро возвращать управление: active objects не превращают длительный вычислительный код в фоновую работу.

Пришлось сделать два соединения: ждать сообщение и отправлять ответ. У приёмного и отправляющего каналов разные задачи. 





CTgPollConn Подключение → AUTH → повторяющиеся POLL



CTgSendConn Подключение → AUTH → один SEND → ответ → закрытие

Два TCP-сокета позволяют отправлять текст, пока приёмный канал ждёт данные. Они не означают, что приложению обязательно нужны два независимых подключения к мобильному оператору.

POLL реализует long polling: сервер отвечает при появлении сообщения либо по истечении ожидания. После END телефон сразу повторяет запрос по тому же соединению. Прокси отвечает в уже открытый телефоном канал, поэтому подключаться к Nokia извне не требуется.

Чтение тоже асинхронное:



TCP возвращает произвольные фрагменты байтов, поэтому один RecvOneOrMore() не равен одному сообщению. Метод Feed() накапливает данные до \n, а затем передаёт готовую строку обработчику. Строка MSG декодируется из UTF-8 в UTF-16 и через движок передаётся интерфейсу.
